DRILLPULSE - ESP32 WI-FI <-> ARDUINO UNO COMMUNICATION
==============================================================

Purpose
-------
Use the ESP32 only as a communication bridge. The ESP32 receives commands
from the laptop over Wi-Fi and forwards them to the Arduino UNO over UART.
Arduino telemetry is forwarded back through the ESP32 to the laptop.

Architecture
------------
Laptop / ROS2 Joystick
        |
        | Wi-Fi / TCP
        v
      ESP32
   Wi-Fi Bridge
        |
        | UART
        v
   Arduino UNO
        |
        v
   HW-130 Motor Driver
        |
      4 Motors

DATA FLOW
---------
Laptop -> Wi-Fi TCP -> ESP32 -> UART -> Arduino
Arduino -> UART -> ESP32 -> Wi-Fi TCP -> Laptop


1. UART BAUD RATE CONFIGURATION
--------------------------------

Recommended Arduino <-> ESP32 UART speed:

    BAUD RATE = 115200
    FORMAT    = 8 data bits, No parity, 1 stop bit (8N1)

Why 115200?
- Much faster than the previous 9600 baud.
- Low communication latency.
- More than enough bandwidth for joystick commands and telemetry.
- Suitable for continuous real-time communication.

Both sides MUST use exactly the same UART settings.

ESP32:
    Serial2.begin(115200, SERIAL_8N1, RX_PIN, TX_PIN);

Arduino UNO:
    Serial.begin(115200);

IMPORTANT:
The Arduino UNO hardware UART is connected to D0 (RX) and D1 (TX).
Do not use Serial Monitor on the UNO at the same time as the ESP32 UART
bridge, because both use the same hardware serial pins.

If 115200 is unstable because of wiring/electrical noise, use:

    57600 baud

Do NOT increase the baud rate unnecessarily. 115200 is the recommended
starting point for this project.


2. UART WIRING
--------------

ESP32 DevKit V1:
    GPIO17 = UART2 TX
    GPIO16 = UART2 RX

Connections:

    ESP32 GPIO17 TX  -----------------> Arduino D0 RX
    Arduino D1 TX ---- voltage divider -> ESP32 GPIO16 RX
    ESP32 GND ------------------------> Arduino GND

IMPORTANT VOLTAGE LEVEL:
Arduino UNO TX is approximately 5 V.
ESP32 GPIO input is 3.3 V logic.

Never connect Arduino D1 TX directly to ESP32 GPIO16 RX.

Example voltage divider:

    Arduino D1 TX
         |
        1k ohm
         |
         +------------> ESP32 GPIO16 RX
         |
        2k ohm
         |
        GND

ESP32 TX at 3.3 V can normally be read by the Arduino UNO RX.


3. WIFI MODE
------------

Recommended first setup: ESP32 Access Point (AP) mode.

The ESP32 creates its own Wi-Fi network. The laptop connects directly
to that network.

Example:

    Wi-Fi SSID: DRILLPULSE_ROVER
    Wi-Fi Password: DrillPulse123
    ESP32 IP: 192.168.4.1
    TCP Port: 5000

This is recommended for rover testing because it does not depend on a
home/college Wi-Fi router.

Connection:

    Laptop
       |
       | Wi-Fi
       v
    DRILLPULSE_ROVER
       |
       v
    ESP32 (192.168.4.1:5000)


4. WIFI SETUP - ESP32
---------------------

The ESP32 should:

1. Start its Wi-Fi Access Point.
2. Use a fixed AP IP such as 192.168.4.1.
3. Start a TCP server on port 5000.
4. Wait for the laptop to connect.
5. Forward received TCP bytes directly to Arduino UART.
6. Read Arduino UART continuously.
7. Forward Arduino bytes to the connected TCP client.
8. Automatically accept a new client if the old client disconnects.

The bridge should NOT modify command contents.

Example command data:

    CMD,0.000,1.000

    CMD,0.500,0.700

    SPEED,150

    STOP

    PING


These strings should pass through unchanged.


5. TCP COMMUNICATION
--------------------

Use TCP rather than UDP for the first implementation.

Reason:
- Commands are not silently lost.
- TCP automatically handles packet ordering.
- Simple Python socket communication.
- Suitable for the current joystick command rate.

Recommended:
    TCP server IP = 192.168.4.1
    TCP server port = 5000

Laptop connects to:

    192.168.4.1
    port 5000


6. LAPTOP WIFI SETUP
--------------------

On Windows:
1. Turn on Wi-Fi.
2. Search for:
       DRILLPULSE_ROVER
3. Connect using:
       DrillPulse123
4. Open the Python/ROS2 joystick program.
5. Configure the communication target:
       IP = 192.168.4.1
       PORT = 5000
6. Replace the old Bluetooth /dev/rfcomm0 communication with a TCP socket.

On Ubuntu:
1. Open Wi-Fi settings.
2. Select:
       DRILLPULSE_ROVER
3. Enter:
       DrillPulse123
4. Verify the connection.
5. Configure the Python program for:
       192.168.4.1:5000


7. COMMUNICATION PROTOCOL
-------------------------

Keep the existing DrillPulse command protocol.

Movement:
    CMD,X,Y


Example:
    CMD,0.000,1.000


Speed:
    SPEED,n


Example:
    SPEED,150


Stop:
    STOP


Ping:
    PING


Arduino telemetry can use the existing lines, for example:

    ENV,...
    ULTRA,...
    GAS,...
    STATUS,...

The ESP32 should treat these as raw bytes and forward them without
changing the contents.


8. REAL-TIME / LOW-LATENCY CONFIGURATION
-----------------------------------------

For seamless joystick operation:

ESP32 UART:
    115200 baud

TCP:
    Persistent connection
    No reconnect for every command
    Keep one TCP socket open while driving

Joystick:
    Send commands continuously, approximately 20-50 times/second.

Recommended command rate:
    50 Hz

That means approximately one movement command every 20 ms.

Example:
    CMD,0.000,1.000

    CMD,0.020,0.980

    CMD,0.040,0.960

    ...

Do NOT add unnecessary delays in the ESP32 bridge.

The ESP32 loop should continuously service both directions:

    TCP -> UART
    UART -> TCP

Avoid delay(100), delay(500), etc.


9. CONNECTION STABILITY
-----------------------

The ESP32 bridge should automatically recover if the laptop disconnects.

Recommended behavior:

If TCP client disconnects:
    - Stop forwarding to that client.
    - Keep the ESP32 Wi-Fi AP running.
    - Keep Arduino UART running.
    - Wait for a new TCP client.
    - Accept the new client automatically.

Do not repeatedly restart Wi-Fi.

Do not restart the ESP32 every time a TCP client disconnects.

For safety, the Arduino should have its own command timeout.

Recommended Arduino command timeout:
    300-500 ms

If no valid movement command is received within the timeout:
    stop all motors.

This prevents the rover from continuing to drive if Wi-Fi or the laptop
fails.

IMPORTANT:
Do not remove the Arduino safety timeout just to make communication
appear seamless. The timeout is a safety feature.


10. POWER AND ELECTRICAL STABILITY
----------------------------------

Communication problems can be caused by motor electrical noise and
voltage drops.

Recommended architecture:

Motor power supply
        |
        +---- HW-130 ---- Motors

Separate regulated supply
        |
        +---- ESP32
        +---- Arduino logic

All grounds must be common:

    Motor supply GND
          |
          +---- Arduino GND
          |
          +---- ESP32 GND

Do not power the motors from the ESP32.

Large motor current spikes can reset the Arduino or ESP32 and appear as
communication disconnects.


11. STARTUP SEQUENCE
--------------------

Use this startup order:

1. Power Arduino + motor system.
2. Power ESP32.
3. ESP32 starts DRILLPULSE_ROVER Wi-Fi AP.
4. ESP32 starts TCP server at 192.168.4.1:5000.
5. Arduino starts UART at 115200.
6. Laptop connects to DRILLPULSE_ROVER.
7. Laptop connects to 192.168.4.1:5000.
8. Laptop sends PING.
9. ESP32 forwards PING to Arduino.
10. Arduino responds with its normal response/telemetry.
11. ESP32 forwards the response to laptop.
12. Joystick control starts.


12. BASIC CONNECTION TEST
-------------------------

Before testing motors, test communication only.

From the laptop, connect to:

    192.168.4.1:5000

Send:

    PING


Then send:

    CMD,0.000,0.000


The Arduino should receive the same text.

Only after this works reliably should the motor commands be tested.


13. MOTOR TEST
--------------

Send:

    SPEED,150


Then:

    CMD,0.000,1.000


For stop:

    STOP


Always test with the rover wheels lifted first.

Verify:
- Forward
- Backward
- Left
- Right
- Stop
- Speed change


14. TROUBLESHOOTING
-------------------

Problem: Wi-Fi network does not appear
Check:
- ESP32 is powered.
- ESP32 AP code is running.
- SSID is correct.
- Restart ESP32 once during development.

Problem: Wi-Fi connects but TCP does not connect
Check:
- IP = 192.168.4.1
- Port = 5000
- Laptop is connected to DRILLPULSE_ROVER.
- TCP server is running.

Problem: TCP works but Arduino receives nothing
Check:
- ESP32 TX -> Arduino D0.
- Common GND.
- Both UART baud rates are 115200.
- Arduino is not using another conflicting Serial configuration.

Problem: Arduino receives garbage
Check:
- Both sides use 115200, 8N1.
- Ground is connected.
- Wires are short.
- Voltage divider is correct.
- Reduce to 57600 if necessary.

Problem: Arduino receives commands but ESP32 does not receive telemetry
Check:
- Arduino D1 TX -> voltage divider -> ESP32 GPIO16.
- Common GND.
- Arduino Serial is configured correctly.

Problem: Motors suddenly stop
First check:
- Arduino command timeout.
- Wi-Fi/TCP connection.
- Motor power supply.
- Voltage drops.
- Motor electrical noise.
- Loose GND.

Problem: ESP32/Arduino resets when motors start
This is usually a power/noise issue, not a baud-rate problem.
Separate motor and logic power and keep grounds common.


15. RECOMMENDED FINAL SETTINGS
------------------------------

Communication:
    Wi-Fi: ESP32 Access Point
    SSID: DRILLPULSE_ROVER
    Password: DrillPulse123
    ESP32 IP: 192.168.4.1
    TCP Port: 5000

UART:
    Baud: 115200
    Format: 8N1
    ESP32 TX: GPIO17
    ESP32 RX: GPIO16
    Arduino RX: D0
    Arduino TX: D1 through voltage divider

Joystick:
    Command protocol: CMD,X,Y\n
    Speed protocol: SPEED,n\n
    Stop protocol: STOP\n
    Suggested update rate: 50 Hz

Safety:
    Arduino command timeout: 300-500 ms
    ESP32: automatic TCP client reconnection
    No unnecessary delays in bridge loop


16. IMPORTANT DESIGN PRINCIPLE
------------------------------

The ESP32 is ONLY a communication bridge.

It should NOT:
- Control the motors.
- Calculate joystick motor directions.
- Change CMD values.
- Add artificial delays.
- Restart Wi-Fi unnecessarily.
- Reinterpret Arduino telemetry.

The Arduino remains responsible for:
- Motor control.
- Command parsing.
- Safety timeout.
- Sensors.
- Telemetry generation.

The laptop/ROS2 node remains responsible for:
- Joystick input.
- Generating CMD,X,Y.
- Sending SPEED commands.
- Receiving telemetry.

    Arduino
       |

This configuration gives a simple, fast, two-way communication path
while keeping the existing DrillPulse motor-control functionality on
the Arduino.
